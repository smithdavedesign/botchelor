# Image strategy

What Botchelor's visual assets are, where they come from, and what has to be true before a hosted
image reaches a page. Written for whoever picks up the visual side of this repo next.

## The decision

**First-party assets only.** Every image-shaped thing in the product is either drawn from character
data by our own code, generated by us and reviewed by a human, created by the creator who owns the
character, or openly licensed with its terms recorded.

Competitor imagery is **research only**. Studying layouts, discovery cards, category structure and
art direction is fair game and shaped the current design; republishing anyone's characters or assets
is not. Public visibility is not a licence, and some image platforms specifically prohibit compiling
their images into a competing service.

| Source                  | Use                                                | Status                  |
| ----------------------- | -------------------------------------------------- | ----------------------- |
| Drawn from our own data | Avatars, venue backdrops, share cards              | **Shipped** ($0)        |
| AI-generated by us      | Character portraits, expressions, backgrounds      | Deferred (needs spend)  |
| Creator-uploaded        | Personal characters and original art               | Deferred (needs review) |
| Openly licensed         | Backgrounds, locations, decorative assets          | Allowed, with terms recorded |
| Competitor imagery      | Studying design only                               | Never republished       |

## What ships today, at $0

No image file is hosted, uploaded or generated anywhere in the product. The visuals are computed:

- **Avatars** — a gradient, motif and initials derived from a character's id and name
  (`lib/avatar.ts`). Stable everywhere the character appears.
- **The curated look gallery** — twelve hand-picked palettes (`lib/presets.ts`). This is the report's
  "let creators pick from a curated gallery", with a palette standing in for a portrait. Picking
  "Golden hour" sets the avatar colour, the appearance line, the suggested traits and the behavioural
  signals the engine decides dates with.
- **Image training** — a creator can point at a reference image; the browser reads its palette with a
  canvas and keeps only the derived numbers. The image is never uploaded, stored or sent, so there is
  nothing to moderate and no real-person risk. A picked preset and a read image go through the same
  mapping (`traitsFromPalette`), so they land in the same place.
- **The house cast** — fifteen free characters plus two premium ones (`lib/house.ts`), each with an
  archetype, an appearance line and a curated hue. This is the report's "house cast of 12-20".
- **Reusable date venues** — eight locations (`lib/venues.ts`), dealt to a date by its seed, each with
  a two-hue backdrop painted behind the episode's setting. The report's "reuse a library of date
  settings", with the composite drawn rather than rendered from bitmaps.

## The provenance ledger

`character_assets` (`lib/db.ts`, `lib/assets.ts`) is the gate any later hosted image has to pass. It
exists now, empty, so that shipping real portraits later needs no migration and no retrofitted rules.

| Field                          | Why it is there                                        |
| ------------------------------ | ------------------------------------------------------ |
| `character_id`                 | Who it belongs to (`null` for a shared asset)          |
| `kind`                         | portrait, expression, background, decoration           |
| `source_type`                  | drawn, generated, uploaded, licensed                   |
| `source_model`                 | Which generator made it, and which version             |
| `prompt`, `prompt_version`, `seed` | How to make a consistent sibling of it later        |
| `source_url`, `license_name`, `attribution` | Third-party terms and the credit they require |
| `review_status`, `reviewed_at`, `reviewed_note` | A human's decision, and when         |

Enforced in both the schema and `lib/assets.ts`:

- A **licensed** asset cannot be stored without `source_url` and `license_name`.
- A **generated** asset cannot be stored without `source_model`.
- Nothing can be **approved** without a `url` to serve.
- `listApprovedAssets` is the only read path, and it returns approved rows only. There is no function
  that hands a pending or rejected asset to a page.

## If and when portraits get generated

Still deferred, deliberately: generation costs money or a GPU, and hosting creator-visible imagery
needs automated moderation (CSAM scanning plus a real-person classifier) that a solo owner cannot
substitute for. See `docs/upgrade-cost.md`.

When it happens, the shape is: generate offline in batches, review by hand, record each asset with its
provenance, approve the keepers, and serve them from object storage. Never per episode — an episode
being watched must not trigger a generation.

The prompt template to record as `prompt_version` v1:

```
STYLE:
Original illustrated romance-game character portrait.
Consistent line weight, lighting, rendering and framing.

CHARACTER:
Adult fictional character, age {age}.
{appearance}
{archetype}; {traits}.

COMPOSITION:
Head and shoulders, centered face,
simple background, vertical 3:4 crop.

CONSTRAINTS:
Original design; no named franchise characters,
no real-person likeness, no text or watermarks.
```

A shared seed or prompt does not guarantee a consistent character across generations, so every output
is reviewed by a human before approval — which is what `review_status` is for.

## Rules that do not change

- Fictional adults only. No real people, no real-person likeness, no named franchise characters.
- A creator uploading art must confirm they hold the rights to it and to the uses in the terms.
- Every asset is deletable, and deleting a character deletes its assets.
